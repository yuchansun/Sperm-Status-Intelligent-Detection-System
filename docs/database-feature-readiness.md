# 功能清單與資料庫準備狀態

核對日期：2026-10-19（Asia/Taipei）。
依據：使用者提供並保存於 `docs/supabase-columns.json` 的四表結構、先前提供的約束／RLS／bucket 設定，以及目前本機程式（最新提交 77f3331）。本次沒有重新查詢遠端結構、修改資料庫、部署或寄送郵件。

結論：現有四表支援基本病患、檢測、示範結果、病患備註與影像路徑，但尚未完成整份功能清單所需的資料契約。欄位存在、程式讀寫完成、使用者流程完成，是三個不同層次。

## 1. 三項指標與單位：部分具備，定義尚未完成

現有 `analysis_records.density`、`motility`、`morphology` 全為 text；目前分別寫入 `48`、`32%`（未選活動力則 null）、`4%`。`ai_result` 也有一份示範指標，可能形成兩份不同的數據來源。

需先決定：
- 數量是影像中計數、整份檢體總數，還是濃度？目前 density 是濃度，不是獨立的數量欄位。若同時需要數量與濃度，必須分開保存；不能只改標題或憑影像個數換算濃度。
- 活動力是總活動力、前進活動力，還是示範分數？目前只有單一 motility 欄位，無法可靠區別。
- 型態指標目前以「正常型態比例」呈現；它不能同時代表頭身比。

建議資料契約：正式計算值用 numeric，單位以統一規格或明確單位代碼定義；比例採 0–100，無資料採 null，0 表示實際測得零。若要區分未檢測與分析失敗，另加指標狀態或原因。量測原值、修正值及顯示字串分離，頁面／圖表／報告從同一個來源讀取。具體欄位命名與轉換需等單位定案，不直接改掉現有 text，避免破壞既有數據。

## 2. Excel 參考範圍與紅綠燈：未完成

現有 clinical_status 是整筆結果狀態，不能表示每項指標分別的燈號。沒有專用的規則版本、參考範圍、規則來源或每項判讀快照欄位。結果頁的燈號／通過文字目前是固定展示內容，不是依老師 Excel 計算；型態缺值時圓餅圖目前會當成 0，需要修正。

需取得老師 Excel，確認每項指標的單位、上下界、等於門檻時歸類、缺值／失敗規則，以及是否依條件分組。不得自行代入其他參考值。

可採版本化程式設定或資料庫規則表，不必為了燈號一定新增一張表；但每次分析至少應保存所用規則版本及判讀快照，以免規則改動後歷史報告被重新解讀。可先規劃 `reference_rule_version`、`interpretation_snapshot`（JSONB，含各指標燈號、參考範圍與單位）。缺值應有「未判讀」狀態，不當成綠燈或零。

## 3. 測試前選病患、看歷史：關聯足夠，API／導頁不足

已有 patients.id → examinations.patient_id → analysis_records.examination_id 關聯，以及歷史 summary。無需另存一份「病患歷史」資料。

缺少遠端病患搜尋／列表／依 ID 讀取 API、選取病患後帶入草稿、測試前歷史摘要介面。現在新增檢測是依輸入的 national_id 查找及更新病患，不是讓使用者先選病患。現有歷史查詢從 analysis_records inner join，因此無檢測或僅完成病患建檔的人不會出現在歷史列表；選病患必須直接查 patients。

national_id 未有資料庫唯一約束。現有程式可攔截查到的多筆，對新建立資料用穩定 patient_code 降低重複，但仍需確認病患識別規則並檢查既有重複後，再決定唯一約束。可補對應搜尋與外鍵索引，這是效能／一致性工作，並非建立新功能欄位。

## 4. 分析前後影像：欄位足夠，讀寫與畫面未完成

已有 original_image_path、analyzed_image_path、boxes，bucket 為 private。現行只上傳 original_image_path；mapRecord 沒有回傳 analyzed_image_path，PrivateImage 只讀一張圖。結果頁的示範框是瀏覽器疊圖，沒有產生或儲存分析後圖檔。

同學可選：用原圖加 boxes 繪製對照，或產生示範標記圖上傳並儲存 analyzed_image_path。兩者都不需要新增圖片路徑欄位；需補讀寫、對照介面，以及明確的示範標示。影像存物件路徑，顯示時才取得短效 URL，不存永久公開連結。若未來一筆檢測要有多張影像／影片，才需另外設計影像子表。

## 5. 數量與活動力同圖：資料有基礎，前端未完成

有病患關聯、exam_date、created_at 及指標，但沒有獨立數量欄位（見第 1 項）。目前圖表是單一指標切換，只畫一條線；同日多次檢驗還需要保留時間與穩定排序。created_at 是建立時間，不能直接當作採樣時間；如需求包含採樣時間需新增 collected_at，否則圖上明確標示是檢驗日期／建立時間。

三項數據轉成統一數值之後，可由前端畫雙軸折線圖，左右軸各標明單位、兩條線各有圖例，不必新增「趨勢」資料表。缺值採 null 留空，不補零、不憑空連續化。舊資料若單位不同，須先轉換或分開顯示。

## 6. 報告預覽、修改、匯出：缺少可追溯的報告保存設計

現有 analysis_records.summary、clinical_status 可以保存部分文字，但沒有報告版本、編輯者、報告語言或原始／修正內容的區分。現有 PDF 按鈕只顯示「PDF 模擬報告已準備下載」訊息，沒有真的輸出 PDF。

建議在開發前定義可改欄位：先允許摘要、醫師意見及呈現文字；是否允許改量測值需另外定義，不能覆蓋 AI 原始值而不留紀錄。

若修改需儲存，規劃 `report_versions`：id、analysis_record_id、version、content（JSONB，依允許欄位驗證）、language、status、created_by、created_at，以及列印時的病患／指標／規則快照。以保存新版本取代直接覆寫原分析，並確保一筆紀錄的版本號唯一。最小版也可以用報告草稿欄位搭配獨立修改紀錄，但這份草稿及歷程目前同樣不存在。

下載可由當前已保存的版本產生，不一定需要把 PDF 存回雲端；若需保存 PDF，須另設私有 reports bucket／權限與 export_path，exam-images 僅允許影像 MIME，不能直接放 PDF。

## 7. Email 預覽與修改：部分前端已有，持久化不足

現行歷史頁可填收件地址，主旨及內文由程式組合，沒有可編輯主旨／內文的預覽。emailService 有呼叫 EmailJS 的寄送功能；分析結果頁寄信按鈕仍為示範。未看到報告附件實作；目前寄送紀錄僅存本機 localStorage，不是雲端發信歷程。

若只要求當次預覽與修改、不需重開草稿，可只做前端，不強迫新增資料表。若要保存草稿或跨裝置接續，規劃 `email_drafts`：id、patient_id、report_version_id（若寄報告）、to_email、subject、body、language、updated_by、updated_at。

若要實際寄送並追蹤，另外規劃 `email_deliveries`／發送紀錄：id、draft_id、寄送當下內容快照、report_version_id／附件識別、requested_by、status、provider_message_id、sent_at、error_code。寄送服務接受不代表送達，sent／delivered 不可混用，送達需供應商回報。需確認寄單筆還是整份歷史，以及 EmailJS 範本／方案的附件能力；本次未驗證外部服務設定。不可為了附件把私有報告永久公開。

patients 沒有 email 欄位；只有想保存病患預設 Email 時才需補，不影響每次手填收件地址。

## 8. 首頁入口：不缺專用資料欄位

目前首頁按鈕導向 /analysis。要串成「開始 → 選病患／新增 → 看歷史 → 設定本次檢測」，屬於前端路由與第 3 項病患 API 工作，不需新增首頁入口欄位。

## 9. 翻譯與用詞：基礎為前端，報告／Email 保存語言則缺欄位

目前 languageOptions 列繁體中文、英文、韓文。部分病患表單、示範標示、錯誤訊息、Email 內文仍為固定中文，尚非完整三語。

UI 字典與指標術語可維護在前端，不必每句都存資料庫。需要跨裝置保留個人偏好時才新增使用者 language 偏好；保存／寄送報告時則在報告版本與 Email 草稿／發送快照記錄 language，避免之後看不到當時實際輸出的語言。個人備註與醫師輸入內容不應自動改寫或翻譯後覆蓋原文。

## 審核與修改的共通缺口

目前 processing_state 支援待複核／已完成，但 completeCloudRecord 只更新狀態與 updated_at。缺 reviewed_by、reviewed_at、review_note，以及誰可以審核的角色設計。依使用者先前提供的 RLS，登入者可共用查詢／新增／修改；網站上的審核按鈕沒有醫師專屬的資料庫限制。

若要求「醫師已審核」，需在資料庫端驗證審核者角色及原狀態，並由受控更新／函式寫入審核時間與操作者，不能只靠前端傳 user ID。另需定義修改已審核報告後是否撤銷審核、產生新版本或重新送審。病患長期備註不能取代某次檢驗的審核意見。

## 開發前需要定案的四件事

1. 老師 Excel 的原始規則，包括邊界與缺值；目前尚未提供。
2. 數量／濃度、活動力類型、型態指標的確切定義與單位。
3. 報告允許修改什麼、是否允許改數值、是否真的產生 PDF、是否保存每版。
4. Email 是否只做預覽、是否保存草稿、是否實寄，以及是否附報告。

建議順序：先凍結資料契約與指標規格，再由資料庫負責人準備不破壞舊值的遷移與對應 API，最後同學依 API 開發介面。先不要讓前端各頁自行決定欄位名稱、百分比格式或門檻。
